# Movie：実況ボイスチェンジ 要件定義案

確認日：2026-09-15。現在のソース、導入済みIrodori、各製品の公式資料に基づく実装前の設計案。
本書に記載した時間・容量・品質閾値は提案値であり、実測済みの性能保証ではない。

## 1. 目的と対象

ユーザーがアップロードしたMP4から実況だけを取り出し、Voiceで作成・保存した声モデルを使って再合成する。発言内容、感情、話し方、発言の開始時刻と間をできる限り保ち、ゲーム音と合成してMP4をダウンロードできるようにする。

対象は「最大60分、日本語、実況者1人」。リアルタイム処理ではなく、アップロード後の非同期変換とする。

| 項目 | 初期仕様 |
| --- | --- |
| 入力 | MP4を1ファイル。映像と独立した2つの音声ストリームを含む |
| 音声トラック1 | ゲーム音声。変換対象にしない |
| 音声トラック2 | 実況音声。発言解析・声変換の対象 |
| 実況者 | 1人。複数話者・重なった会話は初期対応外 |
| 動画長 | 0秒より長く、最大1,800秒 |
| ファイル容量 | 初期上限20 GiB、環境設定で変更可能。録画ビットレートが大きいので時間上限とは別に管理 |
| 変換先 | 同じユーザーの最新の保存済み `.speaker.safetensors` |
| 標準出力 | 元の映像＋「ゲーム音と変換済み実況を混ぜた音声」1トラックのMP4 |
| 追加出力 | 変換済み実況WAV。編集用の複数音声トラックMP4は後続機能 |

トラックは左右のチャンネルとは異なる。ステレオ音声1本の左をゲーム、右を実況と解釈しない。ゲームと実況がすでに混ざった音声の分離も初期対象外。

## 2. 採用する方式と再現できる範囲

推奨は「発言単位の文字起こし＋感情解析＋同一話者での再合成」。IrodoriはTTSなので、元の声の波形から声質だけを変換する専用Voice Conversionとは異なる。文章・発言境界・感情指示・長さを使って話し方を近づける。

Geminiは音声から感情や話し方を解析できる。Irodoriは話者条件とcaptionによるスタイル条件を組み合わせられる。これを役割分担して使用する。[Gemini Audio Understanding](https://ai.google.dev/gemini-api/docs/audio)、[Irodori公式README](https://github.com/Aratako/Irodori-TTS#voicedesign)

再現の優先順位は、①発言内容、②変換先の声の一貫性、③自然さ・異音の少なさ、④映像とのタイミング、⑤感情・話し方。強い感情指示で声が崩れる場合は指示を弱め、必要ならユーザー確認へ回す。優先順位があることを理由に、台詞の欠落・別人の声・発言同士の衝突を許容しない。

再現を目指す要素：喜び・驚き・怒り・不安・落胆、早口・ゆっくり・囁き・叫び、強調、語尾、間、相対的な声量。
完全一致を保証しない要素：細かなピッチ曲線、すべての息遣い、純粋な笑い声・悲鳴・泣き声、歌唱。

## 3. 現在の環境と着手前の品質条件

確認できた現状：

- `/movie` は準備中ページ。動画アップロード・変換ジョブ・書き出しは未実装。
- Next.jsからIrodoriへサーバー側で通信する仕組み、所有者別の音声資産、Speaker Inversionの学習ジョブは存在する。
- 導入済みIrodoriは `ref_embed` と `caption`、`seconds`、`duration_scale` を受け取れる。`ref_embed` と参照WAVの同時指定は不可。
- 実行環境はWindows、RTX 3080 10GB。FFmpeg/ffprobeは導入済み。
- 現在の使用モデルは `phasefield-audio/Irodori-TTS-v4.1-Anime`。Voiceで正常だった生成設定を品質基準として扱う。
- アプリのGemini接続はVertex AI方式。Movieにも同方式を使用する。

### 保存済み声モデルの品質を先に確かめる

前回の比較でユーザーが正常と確認したのは「新規生成」と「そのWAVを参照した生成」であり、「当時の保存済みモデル」は異音ありだった。新規生成が正常なことだけでは、学習後のモデルが正常だとは判断できない。
また、ウォーターマークや再学習がそのモデルの劣化を起こしたという機序は、比較試験だけでは確定していない。

Movieの長時間処理に進む前に、実際に使用する保存済みモデルで普通の台詞・驚き・早口などの短い試聴を行う。形式検査、無音・クリッピング検査に加えて耳で品質を確認する。同じモデルと生成設定の組み合わせでは確認結果を再利用できる。

モデルに問題がある場合は変換開始前に理由を表示する。新規のランダムな声、別の保存モデル、元実況への自動切り替えは行わない。

### モデルの固定と互換性

- 新しいジョブでは、その時点の最新モデルをサーバー側で取得する。
- 開始時にモデルの実体を所有者専用のジョブ領域へ固定する。現在の資産ストアは新しい声の保存時に旧モデルを削除するため、IDの記録だけでは不十分。コピーまたは保存期限付き参照を、置換処理と競合しない形で取得する。
- ジョブ途中でVoiceの声が更新されても、進行中の動画の声は変えない。
- 学習元のベースモデルと同じチェックポイントを使用する。互換性はテンソル形状だけでは判定しない。
- 今後の声保存時にベースモデル名・revision/hash、Codec、学習設定、試聴確認結果を付与する。メタデータのない既存モデルは未確認として扱う。
- Movieの生成音声をVoiceへ自動保存・再学習しない。

IrodoriはSpeaker Inversionを学習時と同じベースモデルで使う構成を案内している。[Irodori Speaker Inversion](https://github.com/Aratako/Irodori-TTS#speaker-inversion)
現在のAnimeモデルはcaption・絵文字の効き方がベースモデルと異なる場合があると配布元が明記しているため、感情対応表は実モデルで試聴して確定する。[モデルカード](https://huggingface.co/phasefield-audio/Irodori-TTS-v4.1-Anime)

## 4. ユーザーの操作

1. Movieを開く。保存済みの声がある場合は「Voiceで保存した最新の声を使用」と表示。未保存ならVoiceへ案内。
2. MP4を選択しアップロード。容量、時間、映像と音声ストリームを検査。
3. ゲーム音・実況音を別々に試聴できる。初期割り当ては第1音声＝ゲーム、第2音声＝実況。逆の場合だけ入れ替える。
4. 「解析してプレビューを作成」。文字起こしと感情を解析し、代表的な数発言の変換前後を試聴できるようにする。
5. 「全体を変換」。原則自動で進行し、問題のある発言だけ「要確認」として表示。
6. 完成動画を再生し「MP4をダウンロード」。ゲーム音量・実況音量は別々に調節でき、変更時は音声の合成と書き出しだけをやり直す。

詳細パネルでは、発言ごとの原文・読み・感情・開始終了位置を確認し、その発言だけ編集・再生成できる。通常画面にSeed・CFG・APIモデル名などを並べない。

元音声との比較試聴は、変換前と変換後を切り替える。元実況と変換済み実況を同時再生しない。
プレビュー未確認のモデルでは最初の短い試聴が必要だが、発言ごとに確認を要求する流れにはしない。

## 5. 入力検査・音声抽出

- ffprobeでコンテナと全ストリームを検査。拡張子だけで判断しない。
- H.264/HEVCなどMP4内のデコード・再格納可能な映像を扱う。ブラウザで再生できない場合はプレビュー専用の互換動画を作る。最終映像は再エンコードなしを基本とする。
- 音声が2本未満、デコード不可、ファイル破損、時間超過、空音声は開始前に具体的な理由を表示。
- 3本以上ある場合は選択した2本を使用し、他の音声を自動で出力しない。
- 表示上の「トラック1・2」とffmpegのストリーム番号を分けて保存する。`a:0` / `a:1` は音声順序であり、全ストリームの絶対indexとは限らない。
- 映像、ゲーム音、実況の元タイムスタンプ・開始offsetを保存。トラックごとに無条件でゼロ起点へ揃えない。
- 実況は解析用16kHz mono PCMと、時間・声量確認用の高品質PCMを用意する。ゲーム音の解析用ダウンサンプリングはしない。
- 実況のステレオをmonoへ変換する前に逆相・片チャンネル無音を検査し、相殺による声の消失を避ける。
- ゲーム音にも元の実況が混ざっている場合は二重音声が残ることを試聴時に示す。自動音源分離で隠して処理を続けない。

明示的なストリーム指定と映像stream copyはFFmpegの標準機能を利用する。[FFmpeg stream selection](https://ffmpeg.org/ffmpeg.html#Stream-selection)

## 6. 発言単位の分割

30秒などの一定間隔を、最終的な発言区間や合成単位にはしない。

### 採用構成

1. Silero VADのONNX版で発声候補を検出する。
2. faster-whisperの `large-v3` を第一候補として日本語の文字起こしを行う。ゲーム用語の辞書を与え、フィラー・言い直し・短い相槌を残す。
3. WhisperXの日本語対応アライメントで、文章と実音声の文字・単語相当の時刻を合わせる。
4. 無音、句読点、文節境界、声の勢いの切り替わりを組み合わせて発言を確定する。

VADは声の候補を探すものであり、文章の終わりや感情は決められない。逆に、Geminiが生成したタイムスタンプだけを映像同期の正解にしない。
WhisperXの日本語アライメントも誤字、固有名詞、数値、叫びで失敗しうる。未整列部分を一律に均等割りせず、要確認にする。[Silero VAD](https://github.com/snakers4/silero-vad)、[WhisperX](https://github.com/m-bain/whisperX)、[日本語アライメント設定](https://github.com/m-bain/whisperX/blob/main/whisperx/alignment.py)

### 初期チューニング値

- 200〜400ms程度の無音を区切り候補とし、文章との整合で採否を決める。
- 数秒から十数秒を主な合成単位とする。1回の合成上限はまず20秒を目安に実機検証する。
- 長い発言は、20秒で強制的に音を切らず、文節・単語境界へ戻って分ける。1発言が複数の合成区間を持てるデータ構造にする。
- 「えっ」「はい」などの短い発言は短さだけで捨てたり、別の感情の発言へ結合したりしない。
- 分析用の切り出しには前後80〜150ms程度の余白を付ける。音声の切り出し余白と最終配置区間は別管理にして二重再生を防ぐ。
- 発言のない時間を詰めない。60分動画中に長い沈黙があっても元の位置に残す。

Geminiに送る単位は、隣接発言をまとめたおおむね45〜90秒の音声窓とする。APIの上限と文脈に合わせて調整するが、窓の端も発言境界へ合わせる。前後の文脈を重ねた場合はcontext扱いにして、同じ発言を二重登録しない。

## 7. Geminiによる感情・話し方解析

アプリ既存のVertex AI認証とGoogle Gen AI SDKを利用する。音声入力と構造化出力に対応し、当該プロジェクトで使えるFlash系の安定版を短い比較試験で選び、`GEMINI_AUDIO_MODEL` とプロンプトの版を固定する。画像生成用のモデル変数を流用しない。

Geminiへは抽出した実況の音声、仮文字起こし、発言IDと相対時刻を送る。短い窓はinlineの音声1ファイルとして送信する。サイズ上限は実際のVertex API制約とBase64の増分を考慮して検査し、超える場合は窓を短くするか非公開GCSのオブジェクトを使う。Developer APIのFiles APIをVertex AI接続へそのまま持ち込まない。[Vertex AI音声入力](https://cloud.google.com/vertex-ai/generative-ai/docs/multimodal/audio-understanding)

### 発言ごとに保持する情報

| 情報 | 例・目的 |
| --- | --- |
| 発言ID・開始終了時刻 | 音声解析側の値。後続処理でも固定IDを使う |
| 原文と修正候補 | 固有名詞、フィラー、言い直しを保持。要約や台詞の追加は禁止 |
| 感情 | neutral / joy / surprise / anger / fear / sadness / confusion / relief / unknown |
| 話し方 | normal / whisper / shout / laugh / cry / breathy / rushed など |
| 強さ | 弱・中・強、または0〜1の内部値。Irodoriの直接パラメータではない |
| 速さ・声量 | 遅い／通常／速い、相対的な強弱。実測時間や音量と照合 |
| 強調・疑問・間 | 文章中の位置を指定し、区間や表記へ変換 |
| 非言語発声 | 笑い、悲鳴、ため息、息などを台詞と区別 |
| 不確実性 | 聞き取り困難、話者混在の疑い、解析不一致などの理由 |

構造化JSONで受け取り、ID重複、範囲外時刻、未定義ラベル、本文の大量改変、出力打ち切りを検出する。Geminiの自己申告confidenceを校正済みの正解確率とみなさない。
文字修正を採用したらアライメントをやり直す。ASRとGeminiの不一致はユーザーが確認できるようにする。
音声中の指示文は分析対象データであり、ジョブ設定やシステム動作の命令として実行しない。

## 8. Irodoriによる感情付き生成

すべての区間で同じモデルスナップショットを話者条件に指定し、発言ごとのスタイルだけを変える。

基本入力は `input=発言本文`、`voice_asset_id=固定したモデル`、`irodori.caption=短い日本語の話し方指示`。
元の実況WAVをIrodoriの話者参照には使わない。元実況は内容・タイミング・表現の解析用である。

| 元の話し方 | captionの生成例 | 補助表現の候補 |
| --- | --- | --- |
| 通常 | 自然な会話調で落ち着いて話す | 通常の句読点 |
| 驚き | 急に驚いて、勢いよく短く言う | 感嘆符、検証後に😲 |
| 喜び | 嬉しさが伝わる明るい調子で話す | 検証後に😊／😆 |
| 囁き | 声を抑えて、近い距離感で囁く | 検証後に👂 |
| 焦り・早口 | 焦って少し早口に話す | 検証後に⏩ |
| 笑い混じり | 軽く笑いを含みながら話す | 🤭 |
| 落胆 | 声量を抑え、落胆した調子で話す | 語尾・間の調整 |

感情ラベルをそのまま `emotion` 引数として送らず、アプリ側の対応表からcaptionへ変換する。captionに元実況者の性別・年齢・声質を混ぜない。
絵文字は対応モデルの表現制御として存在するが、このAnimeモデルでの効果を検証したものだけを許可する。通常のcaptionを基本とし、複数の強い指示を重ねない。[Irodori表現制御](https://github.com/Aratako/Irodori-TTS#features)

Movie専用の生成プロファイルを作り、現在正常なVoiceの設定・画面は変換処理から変更しない。初期基準は現行RFモデル、40 sampling steps、モデル／Codec FP32、候補1、逐次生成。モデルのrevisionも固定し、異なる推論方式のモデルへ自動更新しない。
Seedは区間と試行番号から決定して記録する。Seedを揃えることを話者固定の代わりにしない。
CFGやcaptionの強度は試聴で決めた範囲だけを使用する。長い区間・強いCFG・複数候補を同時に増やさない。[Irodoriパラメータ](https://github.com/Aratako/Irodori-TTS/blob/main/docs/parameters.md)

## 9. 長さと映像同期

生成音声を順に連結するだけでは時間ずれが累積する。各発言を必ず元動画の絶対時刻へ配置する。

1. 元の発声開始・終了を正とし、その差を生成音声の目標時間にする。
2. 初回生成から `seconds` と解析した話速をIrodori-TTSへ渡す。
3. 生成音声の実際の発声開始・終了を測り、`生成発声時間 ÷ 目標時間` から必要な再生速度を数値で求める。
4. 固定の速度倍率上限では拒否せず、音程を維持する時間伸縮で目標時間へ合わせる。
5. 48kHzのサンプル単位で長さを一致させ、数msのフェードで切り口のクリックを防ぐ。足りない端数は無音で補い、次の発言開始を後ろにずらさない。
6. 時間補正後の音声を再認識し、台詞の欠落があれば別Seedで再生成する。倍率の大きさだけを失敗理由にしない。

同じ発言内に明確な長い間がある場合は、合成区間を分けて位置を固定する。
極短い発言、語尾が長く伸びる叫び、生成の最低長さに満たない相槌も元区間へ合わせる。台詞には最初のWhisper文字起こしを使い、生成後の再認識は行わない。区間自体に矛盾がある場合は要確認にする。

出力用実況PCMは48kHzの共通サンプル位置で配置する。時間軸は元MP4のPTSを基準にし、VFR、開始offset、AACの遅延、音声が動画より短いケースを検査する。`-shortest` で安易に映像末尾を切らない。
FFmpegの `atempo` 等を時間補正に使い、対応範囲を超える倍率は複数段に分けて適用する。[FFmpeg tempo](https://ffmpeg.org/ffmpeg-filters.html#atempo)

## 10. 音質・例外・書き出し

### 音質

- 生成結果の空音声、発声欠落、想定外の長さ、クリッピング、台詞の重複、話者の変化を検査する。
- 生成後の再文字起こしとの比較は行わない。機械的ノイズの不存在を数値だけで保証しない。
- 元実況の声量変化を緩やかに反映する。全発言を同じ音量へ正規化して囁きと叫びの差を消さない。
- 音声の過剰なピッチ補正・ノイズ除去・コンプレッサーを標準処理にしない。
- 最終ミックスのtrue peakを初期目標 -1 dBTP以下に収め、AACエンコード後も確認する。元ゲーム音の内容とステレオ定位を保ち、必要なミックスの音量調整は明示する。

### 判定できない発言

聞き取れない部分を推測で創作しない。笑い・悲鳴・ため息・泣き声・息遣い・咳はGeminiで種類を判定し、Irodoriの対応する絵文字制御とcaptionで再生成する。生成後もGeminiで該当の非言語発声が自然に含まれることを確認する。
自動再試行は各区間最大2回追加まで。純粋な非言語発声は失敗区間だけやり直し、それでも不良なら元音声を使用せず自動的に無音化する。台詞を含む区間は台詞まで消さず「要確認」にする。
要確認箇所には、テキスト／読み／感情の修正と再生成を用意する。解決できない区間は無音化できるが、元実況音声の使用はユーザー操作、フォールバック、過去ジョブとの互換処理を含めて許可しない。
未解決区間を隠したまま全体を完成扱いにしない。

### 出力

標準MP4は映像をstream copyし、ゲーム音と変換済み実況を混ぜた48kHz stereo AAC（初期192kbps）をデフォルト音声1本として格納する。2本の音声トラックを入れただけでは同時再生を前提にできないため、標準はミックス音声とする。
元実況は通常の出力に含めない。映像の解像度、フレーム順序、時間、元ゲーム音の位置関係を維持する。音声はミックス・AAC圧縮を行うため、元ゲーム音のバイト列そのままの保存は約束しない。
書き出しは一時ファイルへ行い、ffprobeとデコード検査の成功後に完成ファイルへ切り替える。再生時間、音声track数、default設定、冒頭・中盤・末尾を検査する。

## 11. バックエンド構成と処理継続

```text
Movie画面（Next.js）
    ↓ アップロード・ジョブ操作・進捗
Movie API（所有者確認）
    ↓ 永続ジョブ
Movieワーカー（Python、独立環境）
    ├─ FFmpeg / ffprobe：検査・抽出・ミックス・MP4
    ├─ Silero / faster-whisper / 日本語aligner：発言と時間
    ├─ Vertex AI Gemini：感情・話し方
    └─ 既存Irodoriサーバー：固定モデルでの再合成
```

- 60分動画の処理をNextの1リクエスト内で完了させない。
- Movieワーカーは別プロセス・別Python環境とし、ASR導入で現在動くTTSの依存パッケージを変更しない。バージョンをlockする。
- 初期の単一PCではSQLite（WAL）＋非公開ディスクを採用。トランザクション、ジョブlease、heartbeatで多重実行を防ぎ、処理済み区間を保存する。
- アップロードはチャンクまたはストリームで受け、MP4全体を `request.formData()` / `arrayBuffer()` でメモリへ読み込まない。再送確認と総容量検査を行う。本番オブジェクトストレージでは署名付き再開可能アップロードを使用。
- GPUはRTX 3080 10GBを前提に、初期Movie同時実行数1、Irodori同時合成1。CPUのVADとアライメント、Gemini待ち時間は可能な範囲で並行化する。
- 最初のASR動作基準はCPU int8。GPU化する場合は、Irodoriの生成・学習と共通の排他を取得してモデル解放まで管理する。単に別プロセスで順番に呼ぶだけでは常駐GPUメモリは空かない。
- Voiceの学習中にMovie生成を開始しない。既存のWorkloadGateに従い、Movieは「生成サーバーの空き待ち」を表示する。OSレベルで動くASRは既存のプロセス内ロックだけでは保護されない。
- Gemini 429/一時障害は回数上限付きバックオフ。GPU不足は同じ条件で無限再試行しない。正常Voiceのモデルや精度を自動変更して回避しない。
- ブラウザを閉じても処理を継続。再起動時は保存済みの工程・区間から再開する。処理中だった1区間だけ再試行可能にする。
- キャンセル時は新規処理を止め、停止できる子プロセスを終了。停止不能な推論は終了まで待ってからGPU利用権を解放する。

状態例：`uploading → validating → analyzing → preview_ready → queued → synthesizing → mixing → completed`。分岐として `needs_review / failed / cancelling / cancelled / expired`。
進捗は工程、完了発言数／総発言数、失敗件数で表示する。残り時間は実測が集まってから推定し、固定の「60分動画なら何分」とは表示しない。

### API案

| 操作 | API例 |
| --- | --- |
| アップロード作成・チャンク送信・完了 | `/api/movie/uploads` と配下のエンドポイント |
| 入力検査と保存モデル確認 | `POST /api/movie/uploads/{id}/inspect` |
| 解析ジョブ作成 | `POST /api/movie/jobs` |
| 状態・発言一覧 | `GET /api/movie/jobs/{id}`、`GET .../segments` |
| プレビュー・全体変換開始 | `POST .../preview`、`POST .../convert` |
| 発言修正と再生成 | `PATCH .../segments/{segmentId}`、`POST .../segments/{segmentId}/regenerate` |
| キャンセル／再開 | `POST .../cancel`、`POST .../resume` |
| 再生／完成ファイル | `GET .../preview`、`GET .../download`（Range対応） |
| ファイルとジョブ削除 | `DELETE /api/movie/jobs/{id}` |

ID・所有者・操作の冪等キーを検査する。MovieワーカーからIrodoriへ長さ・Seed・caption等を直接送る専用クライアントを作り、現在のVoice用生成リクエストはそのまま保つ。

### 最低限の永続データ

- jobs：owner、入力hash、映像／音声stream index、元PTS、出力設定、状態、エラー、heartbeat、期限。
- voice snapshots：モデルhash、ベース／Codec revision、生成プロファイル、確認結果。
- segments：発言IDと版、開始／終了サンプル、原文／読み、感情・話し方、alignment評価、要確認理由、出力パス、実測長、試行履歴。
- analyses：Geminiモデル、プロンプト／schema版、窓の範囲、利用量、応答の検証結果。
- artifacts：private storage key、hash、サイズ、保持期限。

## 12. データ管理・運用

既存の所有者cookieと同じスコープで、入力動画、声モデル、解析結果、完成動画を管理する。推測できるファイルパスやpublicディレクトリへの保存は避ける。
初期は元動画・中間素材・出力を完成／キャンセル後24時間保持し、期限と削除操作を表示する。レビュー待ちは最終操作から24時間を初期期限とし、処理中のファイルはleaseが生きている限り削除しない。学習済み声モデル自体はMovieの一時ファイル掃除で削除しない。

実況音声をGoogleへ送信して解析することは利用規約とプライバシー情報に記載し、Movieページでは操作ごとの確認を要求しない。アプリ管理のGCS一時オブジェクトはジョブ期限に合わせて削除し、Google側の保持は利用サービスの設定・契約に従う。ログへ認証情報や音声本文をむやみに出力しない。
FFmpegは引数配列で起動し、ユーザーのファイル名・Geminiの返答をシェルコマンドにしない。
処理前に入力、出力、PCM、中間素材を含めた必要容量を見積もり、空き容量不足はアップロード／変換開始前に通知する。

現状TTS拡張は別リポジトリのローカルコミットにしかないため、Movie提供時には必要なサーバーrevisionと導入手順を再現可能な形で保存する。公式最新版のインストールだけで本システムの全APIが揃うとはみなさない。

## 13. 受け入れ条件

### 機能・同期

- 日本語・1人実況・正しい2音声トラックを持つ60分MP4を、アップロードから完成MP4まで処理できる。
- 全発言で同一モデルhashを使用する。変換中のVoice更新でモデルが入れ替わらない。
- 標準MP4でゲーム音と変換後の実況が同時に聞こえ、元実況トラックは出力に含まれない。
- 固定秒数を理由に単語途中で切断しない。次発言へのはみ出し、無音区間の詰め、発言の二重配置がない。
- 明瞭な発言を人手で時刻付けした評価セットで、開始誤差150ms以内・終了誤差250ms以内を95%以上で目指す。まず短尺試験で閾値を確定し、未達箇所を隠さない。
- 書き出し全長は元映像に一致し、コンテナ・Codecの丸めを含む末尾差は100ms以内を初期目標とする。冒頭・中盤・末尾で累積ずれがない。
- 映像stream copyの場合は映像内容・フレームが変化しない。プレビュー用の変換映像を誤って最終出力へ使わない。

### 内容・表現・音質

- 明瞭な実況の試験セットでは、読みを正規化した文字誤り率5%以下を初期目標にする。ゲーム用語の主要な誤りは修正UIで解決できる。
- 無音に架空の台詞を作らない。聞き取れない発言を要確認として扱える。
- 通常、驚き、喜び、焦り、囁き、笑い混じりを含む代表20発言以上を試聴し、声の一貫性、機械音、語尾欠けを確認する。
- 代表試験でcaptionなしより表現が元音声に近く、自然さや話者一貫性を悪化させないことを人の比較試聴で確認する。絵文字の有効化も同じ基準で判定する。
- 純粋な悲鳴、極短い相槌、笑いだけの区間が処理から無言で消えない。

### 継続性・回帰

- 再読み込み・ワーカー再起動・Gemini一時失敗・一部TTS失敗から再開できる。
- 再開と再送でジョブ・生成・課金要求の不要な二重実行を抑えられる。
- 中止後に新しい生成を開始せず、完成していないファイルをダウンロード可能にしない。
- 他の所有者の動画、解析、声モデルへアクセスできない。
- 60分処理の実測時間・GPUピークメモリ・一時ディスク量・Gemini利用量を記録する。リアルタイム速度は受け入れ条件にしない。
- Movie導入後も、Voiceの既存UI、5本の新規生成、試聴・学習・最新モデル保存が正常である。

## 14. 実装順序

1. 保存済みモデル＋captionの品質と互換性を短尺で確認。現在のVoice生成と設定を基準として記録する。
2. 2トラック抽出、発言分割、日本語alignmentを実装。30秒固定切断を使わず時刻を確認する。
3. Geminiの構造化解析とIrodoriの表現対応表を実装。短い比較プレビューを作る。
4. 発言ごとの長さ調整、再生成、元時刻への配置、MP4合成を実装。
5. 大容量アップロード、永続ジョブ、再開、モデル固定、進捗、期限削除を仕上げる。
6. 60分の通し試験、例外試験、Voiceの回帰確認を行って提供する。

最初に確定すべき技術条件は「保存した声モデルでもノイズなく、感情指示を加えて生成できること」。ここを満たしたうえで、発言単位の再合成と同期へ進む。
